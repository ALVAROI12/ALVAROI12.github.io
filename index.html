Why LLMs keep a KV-cache work for next token 0 cache size 0

Generating token n needs attention over every earlier token. Without a cache the model re-encodes all n keys and values each step, so the total work grows as n². With a cache it keeps them, and each new token only costs n dot-products — the price is memory.

The memory figure is real for the model you pick: 2 × layers × hidden × tokens × bytes. On a Raspberry Pi with 8 GB, that number is the whole problem — which is why I built sliding-window, quantized and paged caches for it.

What quantization actually does to weights levels 256 rounding error 0 model size 0

Trained weights cluster in a narrow bell around zero. Quantizing snaps each weight to the nearest of 2ᵇ evenly spaced levels. At 8 bits the snapped histogram sits on top of the original; at 4 bits you can see the staircase, and at 2 bits most of the information is gone.

The error readout is the mean absolute difference between original and snapped weights, computed live on 20k sampled weights (2% of them are outliers, which is why the levels look so sparse at 4 bits: a handful of large weights stretch the range every other weight has to share). The size is what the model would occupy on disk or in RAM at that precision.

A card processor tells you what it will deposit; the bank tells you what landed. Fees, batched deposits and delays mean they rarely match one-to-one. My reconciler runs a cascade of cheap deterministic stages and hands only the leftovers to an LLM with the full context — it never guesses at money.
